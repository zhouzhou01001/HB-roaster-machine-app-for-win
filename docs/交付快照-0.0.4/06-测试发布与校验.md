# 测试、发布与校验

## 自动化测试证据

发布测试必须由 `python scripts/run_release_tests.py` 生成，不再只记录“139/139”文字结论。结构化报告包含：

- 精确开始与结束时间及本地时区。
- Windows、架构、Python 可执行文件和版本。
- 发现数、运行数、通过数、失败数、错误数、跳过数、预期失败和意外成功数。
- 失败、错误和跳过的逐项详情。
- 与当前应用源文件绑定的聚合 SHA-256。
- 完整逐项输出文本。

交付包内固定路径：`06-校验/test-report-0.0.4.json` 与 `06-校验/test-output-0.0.4.txt`。

## 发布阻断规则

- 测试报告不是 `PASS`。
- 失败数或错误数不为 0。
- 测试报告的应用源码哈希与当前应用源码不一致。
- EXE、当前文档或冻结基线缺失。
- 冻结基线复制后任一文件哈希不一致。
- 最终 ZIP CRC 检查失败。

跳过测试不自动视为失败，但必须在发布结论中逐项说明；当前发布目标是跳过数为 0。

## 制品追溯

`release-metadata.json` 记录构建标识、组装时间、已验证环境、应用源码聚合 SHA-256、完整源码 ZIP SHA-256、EXE SHA-256、测试报告 SHA-256 和冻结基线验证路径。`artifact-traceability.md` 提供人工可读矩阵。

## 包完整性

- `MANIFEST.json`：文件路径、大小、修改时间和 SHA-256。
- `MANIFEST.txt`：便于人工查看的同类清单。
- `SHA256SUMS.txt`：覆盖包内所有其他文件，不包含自身。
- 交付 ZIP 同目录 `.sha256`：校验整个外层 ZIP。
- 组装脚本执行 ZIP CRC 检查。

## 人工与实机测试边界

自动化测试不能证明所有硬件、固件、线缆、屏幕缩放和长时间电气环境均稳定。发布前或现场部署时仍须完成面板温度对照、完整烘焙流程、断线恢复、目标分辨率视觉检查及计划生产使用前的长时间连续运行测试。
