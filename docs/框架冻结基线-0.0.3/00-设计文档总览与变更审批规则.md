# 烘焙软件 0.0.3 设计文档总览与变更审批规则

## 1. 基线身份

| 项目 | 内容 |
|---|---|
| 产品版本 | 0.0.3 |
| 文档基线 | 0.0.3-r1 |
| 基线日期 | 2026-08-28 |
| 审批人 | 项目所有者 |
| 状态 | 已冻结 |

本文件是设计文档包的总入口。当前基线由产品与 UI 规范、操作与验收规范、程序架构基线、流程基线、模块设计说明和最终界面截图共同组成。

## 3. 必须申请审批的情况

出现以下任一情况时，必须先向项目所有者提出审批申请：

- 新增功能需要增加、删除或改写任何正式设计文档内容。
- 现有功能的用户流程、按钮行为、状态转换或异常处理发生变化。
- UI 页面结构、信息层级、组件、配色、字体、响应式规则或交互方式发生变化。
- Model S 协议、串口命令、通道映射、采样频率、质量门或 RoR 算法发生变化。
- 数据字段、数据库结构、归档格式、导入导出格式或 PDF 内容发生变化。
- 模块边界、依赖方向、公开接口、线程模型或构建方式发生变化。
- 为解决设计冲突，需要修改任一已冻结的权威描述。
- 拟将历史、实验性或隐藏功能重新开放为正式功能。

## 4. 审批前允许和禁止的动作

审批前允许：

- 阅读和分析现有代码及设计文档。
- 输出问题说明、影响分析、候选方案和文档修改草案。
- 进行不改变产品行为的故障定位。

审批前禁止：

- 修改、替换或删除已冻结设计文档。
- 将新增功能写入权威基线并宣称已生效。
- 在未确认设计影响的情况下改变正式 UI、流程、协议、数据结构或模块边界。
- 用测试结果、临时说明或代码注释绕过设计文档审批。

## 5. 审批申请必须包含的内容

| 字段 | 要求 |
|---|---|
| 变更名称 | 简短、唯一、可识别 |
| 变更原因 | 说明用户价值、缺陷或外部约束 |
| 新增/变化功能 | 明确行为，不使用模糊描述 |
| 影响文档 | 列出需要修改的文件和章节 |
| 影响模块 | 列出源码模块、数据、设备或构建范围 |
| 变更前后对比 | 说明旧规则、新规则和兼容策略 |
| 风险 | 包括设备、数据、UI、回归和发布风险 |
| 验证方案 | 列出功能测试、单元测试、设备测试和分辨率测试 |
| 版本建议 | 说明是否需要提升程序版本或文档基线版本 |

## 6. 审批状态

审批状态只能使用以下值：

| 状态 | 含义 |
|---|---|
| `待审批` | 仅形成提案，不得修改权威基线 |
| `已批准` | 项目所有者明确同意所列范围，可以实施 |
| `有条件批准` | 只能按项目所有者列出的条件实施 |
| `驳回` | 不得实施，不得改写基线 |
| `已实施待验收` | 代码和文档已按批准范围完成，等待验证 |
| `已验收` | 验证通过，可生成新的冻结基线 |

只有项目所有者的明确回复才构成批准。智能体、测试结果、代码合并或默认沉默均不构成批准。

## 7. 批准后的执行顺序

1. 固化审批记录和批准范围。
2. 按批准内容更新设计文档草案。
3. 按文档实施代码变更，不得扩大范围。
4. 执行批准方案中的测试和设备验证。
5. 对照批准内容逐项验收。
6. 更新程序版本、文档基线版本和变更摘要。
7. 重新生成设计文档包和 SHA256 清单。
8. 经项目所有者确认后，将新包标记为冻结基线。

## 8. 无需改写设计文档的维护

纯内部修复只有在同时满足以下条件时，才可不改写设计文档：

- 不新增、删除或改变用户可见功能。
- 不改变 UI、操作流程、设备协议、数据字段和导出结果。
- 不改变模块公开接口、状态机和持久化边界。
- 对现有冻结规则只是实现纠错，且测试证明行为回到基线。

若是否需要改写存在争议，一律按“需要审批”处理。

## 9. 文档包排除项

以下内容不属于权威设计基线：

- `build/`、`dist/`、`tmp/` 和 `_analysis/extracted/` 中的生成物。
- 第三方库许可证、图标、QML 资源和 PyInstaller 解包内容。
- 历史迭代截图、临时 QA 截图和未标记为最终版的设计稿。
- Codex 运行状态、测试缓存和临时审计脚本输出。

## 10. 冻结声明

0.0.3-r1 设计文档包是当前程序设计与框架的权威记录。后续新增功能若需要改写设计文档，必须先向项目所有者申请审批；未获明确批准，不得修改本基线。
